# QualityForge 全面测试方法论

对**已完成开发**的项目执行系统性测试，产出"可逐条勾选、按优先级标注严重度"的报告，
并把它作为开发者与 Harness 协商修复范围的依据。

## 何时使用

- 用户要求"对某个项目做全面测试 / 质量审计 / 上线前检查 / 验收检查 / 回归评估"；
- 用户希望把质量要求变成可勾选、可跟踪、可交接的清单；
- 需要为一次发布、一次交付或一次开源做质量取证。

不适用：需求尚未成型的早期原型（此时应先做需求与验收标准）；单点 bug 排查（直接定位更快）。

## 核心原则

1. **证据优先**：每条结论都要能回答"凭什么"。命令输出、文件行号、请求响应、日志片段都算证据；
   "看起来没问题"不算。
2. **穷尽优先于抽样**：能展开的测试项要展开（`depth=exhaustive`），宁可多判定几条也不留盲区；
   裁掉的项必须写明原因，**不能把"没测"伪装成"通过"**。
3. **区分三件事**：`未通过`（项目的问题）、`阻塞`（环境/依赖缺失，无法判定）、`待测试`（还没做）。
   工具没装属于阻塞或待测，**不是缺陷**——把环境问题写进缺陷清单会直接损害报告可信度。
4. **可交付判据清晰**：P0 阻断级必须清零；P1 严重级应在本次迭代修复；P2/P3 明确排期或接受风险。
5. **修复范围可协商**：报告默认把"未勾选项"视为待修范围，开发者可以只勾选一部分，
   或用 WONTFIX / DEFER 表达取舍。

## 工作流

```
qf_scan  →  qf_plan  →  qf_exec / qf_probe  →  qf_record  →  qf_report  →  qf_fixplan
  侦察        测试项全集      自动检查 + 探针         深度分析记录      报告        修复波次/交接单
```

### 1. 侦察（qf_scan）

先跑侦察，拿到技术栈、项目类型、可执行命令与**已确认的工程缺口**。侦察结论全部来自磁盘证据；
缺口（如"没有锁文件""缺少 LICENSE"）会随后被生成成测试项。

### 2. 生成测试项（qf_plan）

- 深度选择：
  - `smoke` —— 只看阻断项。上线前的快速过关，几十条。
  - `standard` —— 常规交付审计（默认）。
  - `deep` —— 重要版本的深度审计。
  - `exhaustive` —— **首次全面审计 / 合规取证**：展开全部用例（上千条）。
- 项目类型裁剪：CLI 项目不会出现"多区域容灾"这类不适用项；被裁掉的项会写进报告第 6 节。
- 重复调用安全：已有测试项保留状态与历史，只补新项。

### 3. 自动执行（qf_exec / qf_probe）

- `qf_exec` 只跑侦察识别出的预设命令（build / typecheck / lint / format-check / test / coverage /
  e2e / audit / secrets / outdated），结果自动回填对应测试项。
- `qf_probe` 只探测**本机回环地址**上的服务：先用 bash 在后台启动服务，再验证健康检查与关键路由。
- 需要跑自定义命令时用 bash 工具执行，再用 `qf_record` 把结论写进测试项。

### 4. 深度分析并记录（qf_record）

这是审计的主体工作量：读代码、比对配置、分析日志、构造用例，然后逐条记录。
**批量记录**（一次几十条）比逐条调用高效得多。

记录质量的最低要求：

| 字段 | 要求 |
| --- | --- |
| `status` | fail / pass / blocked / na 之一。判定不了就写 blocked 并说明缺什么，不要猜。 |
| `actual` | 实测事实：看到什么、与期望差在哪里。带文件与行号更好。 |
| `evidence` | 至少一条：命令输出、代码位置、配置片段、日志、响应。 |
| `repro` | 未通过项必须给复现步骤，否则开发者无法独立确认。 |
| `recommendation` | 修复方向（改哪里、怎么改、注意什么），而不是"请修复"。 |
| `files` | 涉及文件（可带行号），便于直接定位。 |
| `effort` | 工作量估计（S/M/L 或人日），用于排期。 |

### 5. 出报告（qf_report）

报告结构与用途：

| 章节 | 用途 |
| --- | --- |
| 0 使用说明 | 告诉开发者怎么勾选、怎么把报告发回 Harness |
| 1 结论摘要 | 交付判定（不可交付 / 未完成 / 有条件交付 / 可交付） |
| 2 优先级与严重度分布 | 一眼看清风险结构 |
| 3 修复波次 | 建议的修复顺序（Wave 1 阻断级清零 → …） |
| 4 问题清单 | **逐条勾选**，每条带期望、实测、证据、复现、建议 |
| 5 全部测试项核对表 | 覆盖度证明：每条测试项与其结论 |
| 6 未展开项 | 被裁剪的项与原因（透明，不伪装） |
| 7 执行证据 | 命令、退出码、耗时、失败输出尾部、探针结果 |
| 8 项目画像 | 侦察结论与工程缺口 |
| 9 签署栏 | 修复确认、复测确认、发布批准 |

### 6. 修复范围协商（qf_update sync + qf_fixplan）

1. 开发者把报告里已处理的行改成 `- [x]`（接受风险写 `WONTFIX`，延后写 `DEFER`，不适用写 `NA`）。
2. `qf_update sync=true` 读回勾选：勾选的缺陷 → **已修复待复测**；取消勾选的已关闭项 → 重新打开。
3. `qf_fixplan` 生成波次与**交接单**，scope 即范围：
   - `all` 全部未关闭项；`p0` / `p0-p1` 最小可交付范围；`defects` 仅缺陷；`pending` 补测；`ids` 指定编号。
   - 「除了 QF-003、QF-017 之外全部修」→ `scope=defects` + `excludeIds`。
4. 修复后用 `qf_exec` 复测，把结果置为**复测通过**；只有复测通过才算关闭。

## 反模式（不要这样做）

- ❌ 把"工具没装/环境缺失"记成 fail —— 应记 blocked，并写明缺什么。
- ❌ 只跑自动检查就出报告 —— 自动命令只覆盖不足三成的测试域，其余需要读代码判定。
- ❌ 一次性把上千条都标成 pass —— 没有证据的通过等于伪造结论。
- ❌ 跳过安全域（`sec-*`）或合规域 —— 企业交付中它们通常是 P0 来源。
- ❌ 只报问题不给复现与建议 —— 报告的价值在于让修复可执行。
- ❌ 把 `pending`（待测）留在报告里却宣称"可交付" —— 判定逻辑会把大量待测判为"审计未完成"。

## 工具速查

| 工具 | 作用 | 关键参数 |
| --- | --- | --- |
| `qf_scan` | 侦察项目并生成画像 | `projectPath`、`force` |
| `qf_plan` | 生成测试项全集 | `depth`、`categories`、`includeAll`、`reset` |
| `qf_exec` | 执行预设检查命令并回填 | `presets`、`timeoutMs`、`autoRecord` |
| `qf_probe` | 回环 HTTP 探针 | `urls`、`expectStatus`、`itemId` |
| `qf_record` | 记录/更新测试项结论 | `items[]`（状态、实测、证据…） |
| `qf_list` | 查询与筛选测试项 | `priorities`、`statuses`、`onlyOpen`、`limit` |
| `qf_update` | 更新状态或同步勾选 | `ids`+`status`，或 `sync=true` |
| `qf_report` | 渲染 Markdown + JSON 报告 | `reportPath`、`waveScope` |
| `qf_fixplan` | 修复波次与交接单 | `scope`、`ids`、`excludeIds`、`format` |
| `qf_reset` | 清除审计数据 | `confirm=true`（慎用） |

审计数据固定落在被审计项目的 `.qualityforge/` 目录：
`audit.json`（唯一真相来源）、`QUALITYFORGE-REPORT.md`（可勾选报告）、`report.json`（供 CI 消费）。
